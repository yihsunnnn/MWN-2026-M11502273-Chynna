# CortexDC AI/ML Thermal Management Literature Analysis

> 主題：資料中心熱管理、溫度預測、機櫃容量分析與 CortexDC 對應研究設計
---

## 1. Project Overview

本報告整理資料中心熱管理相關文獻，目的不是單純摘要論文，而是拆解各研究的：

- Research Problem
- Input / Output
- AI/ML Method
- Experiment Design
- Evaluation Metrics
- Research Gap
- CortexDC Mapping

研究目標是判斷目前 CortexDC 可用資料是否能支援 **server-level / rack-level temperature prediction**，並作為後續模型與實驗設計依據。

## 6. AI/ML Methods Summary

| Method | Main Use | Strength | Limitation | CortexDC Stage |
|---|---|---|---|---|
| Persistence | Simple baseline | 不需訓練，容易比較 | 只能假設未來等於現在 | P0 |
| Linear / Lasso | Explainable baseline | 可解釋、速度快 | 難處理非線性 | P0 |
| XGBoost-lag | Tabular thermal prediction | 適合 sensor data、非線性、可用 SHAP 解釋 | 需人工加入 lag features | P1 |
| LightGBM | Large-scale tabular prediction | 訓練快、記憶體效率佳 | 容易 overfit | P1 |
| GRU | Time-series prediction | 適合熱延遲、多步預測 | 需連續時間資料 | P2 |
| LSTM | Long-term sequence prediction | 可捕捉較長熱慣性 | 資料量與調參成本高 | P2 |
| U-Net / INR / PINN | Thermal field reconstruction | 可產生熱圖或連續場 | 需完整熱場標籤或物理條件 | Future Work |
| DQN / PADQN | Cooling / scheduling control | 可做長期最佳化 | 安全風險高，需要 simulator | Future Work Only |

## 7. Why XGBoost-lag?

XGBoost 本身不是時序模型，所以需要加入 lag features，例如：

- `CPU Temp(t-1)`, `CPU Temp(t-5)`
- `Power(t-1)`, `Power(t-5)`
- `Fan RPM(t-1)`, `Fan RPM(t-5)`
- `Inlet Temp(t-1)`, `Inlet Temp(t-5)`

這樣模型才能知道目前 server 是正在升溫、降溫，還是穩定狀態。

Example target:

```text
Input:
CPU Temp(t), CPU Temp(t-5), Inlet Temp(t), Power(t), Fan RPM(t), Rack ID, U Position

Output:
CPU Temp(t+10 min)
```

## 8. Suggested CortexDC Experiment Design

| Experiment | Goal | Design |
|---|---|---|
| Experiment 1 | Data availability check | 檢查 CPU temp、inlet temp、power、fan 是否連續 |
| Experiment 2 | Baseline model | Persistence、Linear Regression、XGBoost-lag |
| Experiment 3 | Temporal model comparison | GRU / LSTM with 30–120 min input window |
| Experiment 4 | Cross-server / rack generalization | 部分 server 訓練，其他 server 測試 |
| Experiment 5 | Hotspot warning | 預測未來 5/10/15 分鐘是否超過 threshold |
| Experiment 6 | Shadow-mode suggestion | 只輸出建議，不直接控制設備 |

## 9. Evaluation Metrics

| Metric | Use |
|---|---|
| MAE | 平均絕對誤差，容易解釋 |
| RMSE | 對大誤差更敏感，適合熱點風險 |
| R² | 檢查模型解釋能力 |
| Hotspot Recall | 是否抓到真正過熱事件 |
| False Alarm Rate | 是否太常誤報 |
| Warning Lead Time | 能提前幾分鐘預警 |
| Inference Time | 是否能即時部署 |
| SLA Violation Rate | 排程或容量建議是否違反限制 |

Recommended first-stage metrics:

```text
MAE, RMSE, R², Hotspot Recall, Warning Lead Time, Inference Time
```

## 10. Research Gaps

| Gap | Literature Status | CortexDC Opportunity |
|---|---|---|
| Input completeness assumption | 多數文獻假設資料完整 | 建立 feature standardization 與 missing mask |
| Single server / testbed limitation | 常在單台 server、dummy rack 或 CFD 上驗證 | 測試多 server、多 vendor、多 rack |
| Power mapping issue | 文獻多數直接取得 clean power data | 比較 Redfish Power 與 PDU active_power |
| Evaluation gap | 多數只看 RMSE / R² | 加入 warning lead time、hotspot recall、false alarm |
| Control risk | 部分文獻直接 VM placement / cooling control | CortexDC 先做 shadow-mode suggestion |
| Sensor heterogeneity | 不同 vendor sensor 命名不同 | 建立 canonical sensor mapping |
| Cross-device generalization | 模型常只在單一 hardware 測試 | 加入 vendor、model、rack、U position metadata |

## 12. Research Position

本研究的核心問題不是提出全新的 AI 演算法，而是：

> 在 CortexDC 實際可取得且不完整的 sensor / power / rack metadata 條件下，是否能建立可解釋、可部署、可評估的 server-level 與 rack-level temperature prediction pipeline？

因此第一階段應聚焦於：

1. Data quality and feature standardization
2. Server-level CPU / inlet temperature prediction
3. XGBoost-lag baseline
4. GRU / LSTM temporal comparison
5. Hotspot warning and lead time evaluation
6. Shadow-mode decision only

Digital Twin、Thermal Map、RL / DQN / PADQN 應列為 future work。
