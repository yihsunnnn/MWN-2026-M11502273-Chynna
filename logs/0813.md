### 2. 建立 SMO 資料選取工具

開始撰寫 `query_smo.py`，目標是直接從：

```text
SMO InfluxDB
URL    : http://<SMO_IP>:<PORT>
Org    : ravi-ric
Bucket : cortexdc-server
```

進行資料選取，而不是重新從原本 CortexDC VM 的 InfluxDB 取得資料。

規劃支援以下功能：

* Measurement 可單選或複選
* Server 可單選或複選
* Sensor 可單選或複選
* Field 可單選或複選
* 輸入 `all` 可全部選取
* 可選擇最近 1h、6h、24h、2d、5d、7d
* 可自訂開始與結束時間
* 自動將台灣時間 UTC+8 轉換為 UTC
* 將查詢結果輸出成 CSV

預期操作流程：

```text
SMO cortexdc-server
        ↓
選擇 Measurement
        ↓
選擇 Server
        ↓
選擇 Sensor
        ↓
選擇 Field
        ↓
選擇時間範圍
        ↓
Query
        ↓
CSV
```

## 遇到的問題

### 問題 1：複選 Server 後無法取得 Sensor

例如選擇：

```text
Lavoisier + Maxwell
```

輸入：

```text
6,7
```

程式會出現：

```text
[ERROR] 找不到可選的 Sensor
```

一開始懷疑是複選格式錯誤，但即使只選擇單一 Server，也可能發生相同問題，因此確認並不是 `6,7` 的輸入方式造成。

### 問題 2：無法判斷是資料不存在還是查詢程式有問題

為確認問題來源，直接對 SMO InfluxDB 執行 Measurement 與 Field 查詢。

查詢結果確認：

```text
server_cpu
server_fan
server_power
server_temperature
```

四個 Measurement 都實際存在於 SMO。

例如最近 24 小時：

```text
server_temperature / temperature_c = 33536 records
server_fan / fan_rpm                = 14107 records
server_power / average_consumed_watts = 2553 records
server_cpu / total_cores            = 48 records
```

因此可以確認：

> 資料同步本身沒有問題，問題是在 `query_smo.py` 產生 Server / Sensor 選單的查詢邏輯。

---

## 問題處理方式

原本使用 InfluxDB Schema API，例如：

```flux
schema.tagValues()
```

依 Measurement、Server 動態取得下一層選項。

但在加入複選條件後，Server / Sensor 的 Predicate 查詢結果不穩定，因此改變處理方向：

```text
先直接查詢 cortexdc-server 的實際資料
        ↓
filter Measurement
        ↓
filter Server
        ↓
取得實際存在的 server_name / sensor_name / _field
        ↓
產生可選清單
```

也就是避免只依賴 Schema 查詢，而是利用 SMO 中實際已同步的資料產生選單。

目前已確認資料本身完整存在，因此後續只需要修正 `query_smo.py` 的動態選單邏輯，不需要修改 CortexDC → SMO 的同步流程。
